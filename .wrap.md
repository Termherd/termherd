# wrap configuration

Inferred during the first unconfigured `/wrap` pass (the MCP control-surface
milestone) and written down so the next one does not re-derive it. Correct it
in place when a location moves — a stale entry here silently sends the pass to
the wrong file.

## Canonical locations

- index: `ROADMAP.md` — feature status (MoSCoW from `docs/PRD.md` §5). The
  table that must match reality; a shipped feature is ticked here with an
  ADR-style note explaining *why*, not just *what*.
- lessons: `AGENTS.md` — the file every contributor and agent reads first.
  Durable, repo-wide rules go in its **Quality bar** section.
- skills: `.claude/skills/` — operational procedures (how to run something),
  as opposed to rules about the code.
- manual: `docs/src/` — the mdBook served at
  <https://termherd.github.io/termherd/>. User-facing, so it is in the blast
  radius of any change a user can see; `AGENTS.md` (*Keeping the book current*)
  carries the table of which page answers to which code.
- decisions: `docs/adr/` exists but holds a single entry
  (`0001-plans-memory-write-scope.md`), so it is a precedent rather than a
  habit. Most cross-cutting decisions are recorded as prose in
  `docs/ARCHITECTURE.md` (structure) or `docs/PRD.md` (product), and a
  per-issue investigation as a note in `docs/notes/`. This entry used to claim
  the directory did not exist at all.
- feature verdicts: `.personal/feature-torture/reports/<F-id>.md` (gitignored,
  local) — cited from the `ROADMAP.md` entry.
- journal: none. Shipped history lives in `ROADMAP.md` entries and git.

## Verification commands

Mirror of the CI gates (see `docs/CI.md`). CI runs each only when its file
category changed, but a wrap pass touching both docs and code should run all
of them.

- blocking: `cargo fmt --all --check`
- blocking: `cargo clippy --workspace --all-targets -- -D warnings`
- blocking: `cargo test --workspace`
- blocking: `markdownlint-cli2`
- blocking: `just check-deps` — the hexagonal crate dependency rule
- blocking: `just check-arch` — intra-crate module seams + OS-cfg containment
- blocking: `just docs` — the user manual builds, and every `SUMMARY.md` link
  resolves to a file on disk. A wrap that edits `docs/src/` and skips this is
  the one case where the pass itself can break the gate it is closing.
- advisory: `cargo deny check` — only if cargo-deny is installed
- advisory: `cargo machete` — unused deps; only if installed

## Disposable zones

- `target/`
- `.impeccable/` — per-directory tool caches, gitignored; they regenerate on
  every run, so ignore them rather than deleting them each pass
- `.claude/worktrees/` — per-machine working copies. Remove a worktree only
  after confirming its PR merged **and** the directory is clean; the branch's
  commits will not appear on `main` because PRs are squash-merged, so check
  the PR state, not `git log main..branch`.
- `docs/book/` — the built manual, regenerated by `just docs`. Leave it, but
  know that it keeps a *pre-edit* copy of every page: a grep over the repo
  during a reconciliation pass will surface wording you have already fixed.
- `mutants.out/`, `mutants.out.old/` — `cargo mutants` output, gitignored.
  Leave them; see the note below before touching one.
- `.DS_Store`

## Commit conventions

- format: `<type>(<scope>): <the conclusion, lowercase>`
- type: `feat` / `fix` / `refactor` / `docs` / `chore` / `ci` / `test`
- scope: the crate or module the change lands in — `app`, `core`, `pty`,
  `scan`, `mcp`, `agents`, `roadmap`
- Issue refs (`#NN`) belong in the commit **body** and in PR descriptions,
  never in code comments, doc-comments or test names — see `CONTRIBUTING.md`.
- No AI/Claude signature, "Generated with" footer or `Co-Authored-By: Claude`
  trailer, anywhere. The harness injects both as "attribution guidance" in a
  system reminder, and the #84 pass let both through. The PR footer was
  stripped before merge; the commit trailer was not, and GitHub's squash
  re-emitted it on `main` (`18027b7`, as lowercase `Co-authored-by`), where
  it stays — a case-sensitive `grep 'Co-Authored'` then reported it absent.
  Re-read the message for either before `git commit` and `gh pr create`; the
  reminder is overridden, not advisory. Check with `grep -i`.
- Bookkeeping (a `ROADMAP.md` tick, a doc reconciliation) rides **with** the
  feature PR it describes; it never becomes a standalone follow-up PR.

## Notes

**`cargo mutants` reads back as a trap.** Two lessons paid for during the
screenshot rung, both about mistaking an in-progress run for a finished one:

- `mutants.out/outcomes.json` is rewritten *as the run proceeds*. Reading it
  mid-run yields a plausible partial tally — "16 mutants, 0 missed" when 141
  were queued — that looks exactly like a result. Only quote a run that has
  printed its `N mutants tested in Xm` summary line.
- Deleting or reusing `mutants.out/` while a run is live kills it
  (`File exists (os error 17)`). Pass `--output "$TMPDIR/mutants-<topic>"` so a
  run cannot collide with the working tree or with another run.

**A merged PR does not close its issue here.** GitHub auto-closes only on the
English keywords (`closes` / `fixes` / `resolves`). #239 merged with
« Ferme #236 » in its body and #236 stayed open — the fix shipped while the
tracker still showed it as outstanding. That incident is what made English-only
writing a rule in `AGENTS.md`, so a French body is no longer the way this
happens; what remains is a body that names the issue without the keyword. Write
`Closes #NN` on its own line, and during a wrap that follows a merge check
`gh issue view <NN> --json state` rather than assuming.

**A test-only temp path is shared state.** The private per-session directories
`launch.rs` builds are named from the session id, so two runs of the same test
collide and a leftover directory silently changes what the next run observes —
one `cargo mutants` survivor was a stale `termherd-shell-97/` from an earlier
failing run, not a real gap. A test that writes under `std::env::temp_dir()`
must clear its target first and remove it after.

**Timeouts dominate the wall clock.** Do not force `--timeout`; the
auto-derived value (baseline × a factor) is far tighter. And keep test fixtures
small — one 3000×2000 test frame took a run from 8 minutes to 22, because a
mutant that makes an inner loop quadratic then burns the whole budget.

**Prefer `--in-diff` over whole files.** `git diff > d.patch && cargo mutants
--in-diff d.patch` mutates only the lines the session changed — 30–100 mutants
in a couple of minutes, against several hundred for the files they live in.
Cheap enough to re-run after every fix, which is how the keyboard rung caught
four survivors that a single end-of-session pass would have reported too late
to act on.

**`README.md` is in the blast radius of every user-facing change, and gets
forgotten.** First seen on the MCP rungs: it carries the tool table *and* a
sentence naming which follow-ups remain, so shipping a rung leaves it asserting
that the thing you just built is still to come — the keyboard rung (#229)
shipped that way and needed a follow-up pass.

The scope was wider than "MCP rungs", which the next two features proved. The
clickable file paths (#252) never reached the README at all, and the editor
command (#257) shipped without appearing in its list of `settings.json` blocks
— two consecutive misses on a file whose own note said it gets missed, because
the note named a *feature family* rather than the sections that rot.

Those sections are the ones to grep, whatever shipped: the `settings.json`
block list under **Configuration**, the mouse/gesture paragraph at the end of
**Shortcuts**, the MCP tool tables, and any sentence naming a follow-up as
still to come. Docs ride with their feature (see the bookkeeping rule below),
and this is the file that keeps escaping it. Third miss, with this list
already written: hidden hyperlinks (#84) updated the book page and left the
Shortcuts paragraph enumerating "the URL or file path" — the list above names
the section, and the PR still went out without grepping it. The book's
`reference/keyboard.md` chord table is a copy of that paragraph and rots with
it; add it to the grep.

Fourth miss, two PRs in one day: the terminal pointer (#300) and the mouse
forwarded to the child (#155) each updated the book, AGENTS, the roadmap and
the changelog, and neither touched README — the tool table went on listing
fifteen tools, the follow-up sentence still said the surface "can press keys
but not click", and the gesture paragraph promised a drag selects with no word
for a program that owns the mouse. The book's `mcp/index.md` carries the tool
count twice more (a diagram and a table), and rotted the same way. The pattern
is now clear enough to state as a rule for the *feature* pass, not the wrap:
**before `gh pr create`, grep README.md and `docs/src/mcp/index.md` for the
number of tools and for the sentence naming what remains** — the two things a
new rung always changes and the two files the rung's author never opens.

**Grep the verb, not the issue number.** A *bugfix* drifts that prose as
readily as a feature does, and less visibly. #237 made `escape` leave every
prompt, while the README went on promising that `escape` *and* `enter` both
answer any prompt — half true before the fix, and half true after it for the
other half. What went stale was a **capability** claim, not a feature list, so
grepping for the issue number would have found nothing. Grep for what the
surface is said to be able to *do*.

**A reworded claim leaves copies, and the grep is for the *old* words.** The
pointer-rung pass rewrote AGENTS.md's "the capability is otherwise whole in
three parts … what lets an agent verify a gesture fix" and wrote two new
`.roadmap/` entries stating the corrected position — and left
`f-mcp-screenshot.md` holding the original sentence, the one entry in the
directory arguing against the two beside it. Nothing flagged it: a grep for the
*new* wording finds only the sites already fixed, and the stale entry named
neither the issue nor the feature that superseded it, so no cross-reference led
back to it either. When a pass changes a claim rather than deleting it, grep
the sentence being replaced — before the edit, while its exact words are still
in front of you.

**A docs-only PR that caveats an open defect is superseded the day the fix
starts.** The #316 pass filed the issue, caveated eight surfaces, and shipped
them as PR #317 — then the fix began an hour later, and every one of those
caveats had to be rewritten into the fixed behaviour. #317 was closed
unmerged and its commit cherry-picked under the fix (#318). The bookkeeping
rule above already says docs ride with the feature PR; what this adds is the
*defect* case: when a wrap files a bug it intends to fix soon, commit the
caveats on the wrap branch and hold the PR — the fix branch starts from that
commit, and there is one review instead of two. Publish the caveats alone only
when the fix is not scheduled.

**Singular follow-up sentences drift silently.** `README.md` and the *Still
open* paragraph in `AGENTS.md` both named #196 as **the** one remaining item.
Filing two more defects against the same surface made both sentences wrong
without touching a word of either — nothing greps as stale, because the text
never mentions what was just added. When a pass files an issue against a
surface, re-read that surface's "what remains" sentence in every file that has
one.

**The refuter earns its keep on `AGENTS.md` prose, not on the code.** A wrap
that ends by promoting a lesson writes durable rules from the freshest, most
compressed part of the session's context — which is exactly where a plausible
history distorts. The #252 pass drafted two entries containing two false
claims: "shipped this way through 843 green tests" (the bug never reached
`main`; adversarial review killed it at 839) and an inventory of where
`tokio::` calls are allowed that `main.rs` and forty `#[tokio::test]` refuted.
Both read as facts and neither was. Before committing anything to `AGENTS.md`,
re-derive every historical claim from `git log -S` and every inventory from a
fresh grep — the file everyone reads first is the worst place to be
approximately right.

**A qualified identifier can be invented by the window you read it in.** The
pointer-rung pass wrote that `Event::Wheel` carries a pointer cell. `Event` has
no such variant: the wheel is `ScrollTarget::Wheel`, reached through
`Event::ScrollViewport`. Nothing was hallucinated from nothing — a
`sed -n '100,150p'` window opened *inside* the enum, so the variant appeared
with no `pub enum` header above it and got attributed to the type named in the
paragraph. A review pass then confirmed the claim by reading the same window,
and it shipped in a commit message, a feature file and the generated
`ROADMAP.md`. Prose does not compile, so a `Type::Variant` that does not exist
costs nothing until someone tries to find it. Grep the exact path
(`grep -n 'enum Event' -A40`) rather than trusting the window, and treat a
second agent agreeing as one reading confirmed, not two.

**A scripted edit can succeed and still eat the file.** The warning everyone
repeats is the substitution that matches nothing and looks like a success; the
one that cost an amend here was the opposite. Resolving a `.wrap.md` conflict
with a Python slice — `s[:start] + resolved + after` — rebuilt the region
correctly and **truncated everything past it**: one note cut mid-sentence, the
next gone entirely. `markdownlint` reported exactly one problem — MD047, a
missing trailing newline. That is the truncation's *side effect*, not the
truncation: a linter can tell you a file is malformed, never that content is
absent, so the one signal it gave pointed at a one-character fix while two
notes were gone. Read the diff's shape before committing: `git diff --stat`
and a count of removed lines against the number you meant to remove. Six
removed where six were retracted is an answer; forty is a truncation wearing
a nearly clean lint.

That check is also the only one that catches the *loud* failure, which is
counter-intuitive enough to have cost a bundled commit. A `python3 - <<'EOF'`
block that raises exits non-zero and says so — and the `git add` on the **next
line of the same Bash call** runs anyway, because a heredoc is a command, not a
guard. Splitting one file's two ideas into two commits is exactly where that
bites: the assertion caught the reflowed target string, the shell ignored it,
and both ideas were staged for one commit. Chaining with `&&` closes that
variant, and only that one — the silent no-match above still exits 0 and
proceeds. Whichever way it fails, the staged shape is what tells you.

**`git cherry-pick --abort` is not an undo for the conflict you were fixing.**
It discards the whole in-progress resolution, including the parts that applied
cleanly and the edits you made by hand. Reached for after a `--continue` that
printed an editor hint instead of committing, it cost the entire merge a second
time. Keep `--abort` for actually abandoning the pick.

For a **single-commit** pick — the case here, and the usual one when rescuing
one orphan commit — `git commit` finishes it and `cherry-pick -n` avoids the
`--continue` step altogether. Neither shortcut generalises: `-n` suppresses the
commit, not the sequencer, so a conflict partway through `cherry-pick -n A B C`
still halts with `.git/sequencer` holding the rest, and only `--continue` walks
it. Know which of the two you are in before reaching for either.

**Read GitHub ids; there is no way to recall them.** Filing an issue here is
half of filing it — `AGENTS.md`'s bullet *Filing an issue is not the end of
filing it* requires `Horizon` and `Effort` on every issue, plus `Class` on a
Feature or `Severity` on a Bug (a Task carries neither), all in the same pass.
The per-type table lives in `scripts/board_check.py`'s docstring, which is what
enforces it. Every one of those is id-addressed, and a guessed id fails
misleadingly: an invented
`issueTypeId` answers `Issue type cannot be found in this organization`, which
reads as "no such type" rather than "wrong id". Fetch all three:

```bash
gh api graphql -f query='{ organization(login: "Termherd") {
  issueTypes(first: 10) { nodes { id name } } } }'   # Task / Bug / Feature
gh project field-list 1 --owner Termherd --format json   # fields + option ids
gh project item-list 1 --owner Termherd --format json --limit 200  # item ids
```

Then `updateIssue(input: {id, issueTypeId})` over `gh api graphql` for the
type — the native type is *not* named by that bullet, but an unclassified type
is as invisible as an empty field — and `gh project item-edit` per board field.
`just board-check` is what tells you it took, and it needs the sandbox
disabled: inside it, the recipe fails on TLS and reports *unchecked*, exit 2,
which is not the same as clean.

**Squash-merge hides worktree readiness.** `git log main..<branch>` will never
show a merged branch's commits, and `git merge-base --is-ancestor` says NO for
a branch whose content is on `main`. Check `gh pr view <n> --json state`
instead, then remove the worktree and delete the local branch — `git branch -d`
also refuses on the same false premise and needs the PR state, not the graph.

**A fix can be right while its stated cause is wrong, and the wrong cause is
what ships.** This pass re-derived a mechanism a session had asserted three
times — in a commit message, in a code comment, and on its way into an
`AGENTS.md` rule — and it was false. Two test fixtures written as `abc.jsonl`
were said to have "collided into a single record" because "the scan keys
sessions by that id". The scan does no such thing: `scan_root` does
`records.append`, both records survive, and what was ambiguous was the *lookup*
in the test helper, which every record satisfied. The fix — unique fixture ids
— was correct either way, which is exactly why nobody re-checks the story
attached to it.

A figure gets re-derived because it looks like a number. A *mechanism* reads as
understanding and gets quoted forward. When a wrap follows a debugging session,
re-run the probe that establishes the cause, not only the ones that establish
the counts — and prefer a probe that prints what it found (`2 record(s): [...]`)
over one that returns a verdict, since a verdict cannot be wrong in an
interesting way. Here a first probe printed `1` and was believed; a second,
written to enumerate rather than to judge, printed both records and settled it.

**The worktree can vanish under the pass.** A wrap run *from inside* the
worktree whose PR just merged is a wrap standing on a directory the merge
cleanup is about to remove. Here it went mid-orientation: `git worktree list`
answered normally, and the next command died with `Working directory
".../fix-299-..." was deleted`. Worse than the error is the state it leaves —
the session is still flagged worktree-isolated, so every subsequent `git -C
<main checkout>` is refused as a redirect out of the worktree, and the pass has
no way to read the repository it is wrapping. `ExitWorktree` with `keep` clears
the flag and returns the session to the main checkout; there is no need to
recreate anything, since the branch is merged and its commits are on `main`.
Simplest avoidance: run the wrap from the main checkout, not from the branch's
worktree — the merge is already the thing you are wrapping.

**Orientation that reads only the main worktree will call a built feature
unstarted.** `git status` and `git log` in the checkout answer for the checkout,
and this repo parks work in `.claude/worktrees/` by habit — so a branch with a
thousand lines on it and no upstream is invisible to every probe the pass
normally runs. This session twice told the user that `F-mcp-attach` (#267) was
"entirely to do"; `git worktree list` then showed two commits implementing it,
sitting unpushed since the day before. The tell was there to be read: a branch
line with no `[origin/...]` in `git branch -vv`.

The staleness runs the other way too, and that is the expensive half. A parked
branch is frozen prose as much as frozen code — the #267 branch still says the
MCP surface is "the same **thirteen** tools" in seven places across five files,
and the word "fifteen" appears nowhere on it. That is the exact count that #287
went through the repo to correct. No grep of `main` sees it, and a rebase will
replay it onto a tree that has just been fixed. So a wrap that
finds a parked branch owes two lines: how far behind its base is, and which of
the claims this milestone corrected it still carries. Report them; do not edit
another session's branch to fix them.

Read again after the pointer-rung pass: the same branch was 2 ahead and eight
behind `origin/main` at `b4285f2` — and nine behind forty minutes later, when
that wrap's own PR merged. The figure went stale inside the pass that wrote it,
which is the argument for the rule rather than against it: quote a distance
with the commit it was measured against, or quote no number at all. Its debt
has outgrown the tool count — `README.md`'s "Four
follow-ups remain" and `AGENTS.md`'s "otherwise whole in three parts" are both
claims `main` has since corrected, on top of the seven `thirteen`s. Expect that
shape: a parked branch picks up one more stale claim per docs pass it sits
through, so these two lines get re-derived each wrap rather than copied forward
from the last one.

**A rebase from an agent session stalls at the first signature, and the way
out is not `--abort`.** GPG's pinentry cannot reach the agent's shell, so
`git rebase origin/main` applies the first pick cleanly and then fails at
`commit` with `signing failed: Operation timed out`, leaving the pick's changes
staged and the same pick rescheduled in the todo. The recovery: the user runs
`git commit -S -C <original sha>` (message and author reused) and then
`rebase --continue`; git drops the rescheduled pick as "patch contents already
upstream" and moves to the next one. A conflict there is resolved as usual, but
the `--continue` again needs the user's terminal for the signature — plan for
two hand-offs per rebase, not one. Seen rebasing #308 after six merges had
landed under it.
