# wrap configuration

Inferred during the first unconfigured `/wrap` pass (the MCP control-surface
milestone) and written down so the next one does not re-derive it. Correct it
in place when a location moves — a stale entry here silently sends the pass to
the wrong file.

## Canonical locations

- index: `ROADMAP.md` — feature status (MoSCoW from `docs/PRD.md` §5). The
  table that must match reality; a shipped feature is ticked here with an
  ADR-style note explaining *why*, not just *what*.
- lessons: `AGENTS.md` — the file every contributor and agent reads first.
  Durable, repo-wide rules go in its **Quality bar** section.
- skills: `.claude/skills/` — operational procedures (how to run something),
  as opposed to rules about the code.
- decisions: this repo has no `adr/` directory. A cross-cutting decision is
  recorded as prose in `docs/ARCHITECTURE.md` (structure) or `docs/PRD.md`
  (product), and a per-issue investigation as a note in `docs/notes/`.
- feature verdicts: `.personal/feature-torture/reports/<F-id>.md` (gitignored,
  local) — cited from the `ROADMAP.md` entry.
- journal: none. Shipped history lives in `ROADMAP.md` entries and git.

## Verification commands

Mirror of the CI gates (see `docs/CI.md`). CI runs each only when its file
category changed, but a wrap pass touching both docs and code should run all
of them.

- blocking: `cargo fmt --all --check`
- blocking: `cargo clippy --workspace --all-targets -- -D warnings`
- blocking: `cargo test --workspace`
- blocking: `markdownlint-cli2`
- blocking: `just check-deps` — the hexagonal crate dependency rule
- blocking: `just check-arch` — intra-crate module seams + OS-cfg containment
- advisory: `cargo deny check` — only if cargo-deny is installed
- advisory: `cargo machete` — unused deps; only if installed

## Disposable zones

- `target/`
- `.impeccable/` — per-directory tool caches, gitignored; they regenerate on
  every run, so ignore them rather than deleting them each pass
- `.claude/worktrees/` — per-machine working copies. Remove a worktree only
  after confirming its PR merged **and** the directory is clean; the branch's
  commits will not appear on `main` because PRs are squash-merged, so check
  the PR state, not `git log main..branch`.
- `mutants.out/`, `mutants.out.old/` — `cargo mutants` output, gitignored.
  Leave them; see the note below before touching one.
- `.DS_Store`

## Commit conventions

- format: `<type>(<scope>): <the conclusion, lowercase>`
- type: `feat` / `fix` / `refactor` / `docs` / `chore` / `ci` / `test`
- scope: the crate or module the change lands in — `app`, `core`, `pty`,
  `scan`, `mcp`, `agents`, `roadmap`
- Issue refs (`#NN`) belong in the commit **body** and in PR descriptions,
  never in code comments, doc-comments or test names — see `CONTRIBUTING.md`.
- No AI/Claude signature or "Generated with" trailer, anywhere.
- Bookkeeping (a `ROADMAP.md` tick, a doc reconciliation) rides **with** the
  feature PR it describes; it never becomes a standalone follow-up PR.

## Notes

**`cargo mutants` reads back as a trap.** Two lessons paid for during the
screenshot rung, both about mistaking an in-progress run for a finished one:

- `mutants.out/outcomes.json` is rewritten *as the run proceeds*. Reading it
  mid-run yields a plausible partial tally — "16 mutants, 0 missed" when 141
  were queued — that looks exactly like a result. Only quote a run that has
  printed its `N mutants tested in Xm` summary line.
- Deleting or reusing `mutants.out/` while a run is live kills it
  (`File exists (os error 17)`). Pass `--output "$TMPDIR/mutants-<topic>"` so a
  run cannot collide with the working tree or with another run.

**A merged PR does not close its issue here.** GitHub auto-closes only on the
English keywords (`closes` / `fixes` / `resolves`). #239 merged with
« Ferme #236 » in its body and #236 stayed open — the fix shipped while the
tracker still showed it as outstanding. That incident is what made English-only
writing a rule in `AGENTS.md`, so a French body is no longer the way this
happens; what remains is a body that names the issue without the keyword. Write
`Closes #NN` on its own line, and during a wrap that follows a merge check
`gh issue view <NN> --json state` rather than assuming.

**A test-only temp path is shared state.** The private per-session directories
`launch.rs` builds are named from the session id, so two runs of the same test
collide and a leftover directory silently changes what the next run observes —
one `cargo mutants` survivor was a stale `termherd-shell-97/` from an earlier
failing run, not a real gap. A test that writes under `std::env::temp_dir()`
must clear its target first and remove it after.

**Timeouts dominate the wall clock.** Do not force `--timeout`; the
auto-derived value (baseline × a factor) is far tighter. And keep test fixtures
small — one 3000×2000 test frame took a run from 8 minutes to 22, because a
mutant that makes an inner loop quadratic then burns the whole budget.

**Prefer `--in-diff` over whole files.** `git diff > d.patch && cargo mutants
--in-diff d.patch` mutates only the lines the session changed — 30–100 mutants
in a couple of minutes, against several hundred for the files they live in.
Cheap enough to re-run after every fix, which is how the keyboard rung caught
four survivors that a single end-of-session pass would have reported too late
to act on.

**`README.md` is in the blast radius of every user-facing change, and gets
forgotten.** First seen on the MCP rungs: it carries the tool table *and* a
sentence naming which follow-ups remain, so shipping a rung leaves it asserting
that the thing you just built is still to come — the keyboard rung (#229)
shipped that way and needed a follow-up pass.

The scope was wider than "MCP rungs", which the next two features proved. The
clickable file paths (#252) never reached the README at all, and the editor
command (#257) shipped without appearing in its list of `settings.json` blocks
— two consecutive misses on a file whose own note said it gets missed, because
the note named a *feature family* rather than the sections that rot.

Those sections are the ones to grep, whatever shipped: the `settings.json`
block list under **Configuration**, the mouse/gesture paragraph at the end of
**Shortcuts**, the MCP tool tables, and any sentence naming a follow-up as
still to come. Docs ride with their feature (see the bookkeeping rule below),
and this is the file that keeps escaping it.

**Grep the verb, not the issue number.** A *bugfix* drifts that prose as
readily as a feature does, and less visibly. #237 made `escape` leave every
prompt, while the README went on promising that `escape` *and* `enter` both
answer any prompt — half true before the fix, and half true after it for the
other half. What went stale was a **capability** claim, not a feature list, so
grepping for the issue number would have found nothing. Grep for what the
surface is said to be able to *do*.

**Singular follow-up sentences drift silently.** `README.md` and the *Still
open* paragraph in `AGENTS.md` both named #196 as **the** one remaining item.
Filing two more defects against the same surface made both sentences wrong
without touching a word of either — nothing greps as stale, because the text
never mentions what was just added. When a pass files an issue against a
surface, re-read that surface's "what remains" sentence in every file that has
one.

**The refuter earns its keep on `AGENTS.md` prose, not on the code.** A wrap
that ends by promoting a lesson writes durable rules from the freshest, most
compressed part of the session's context — which is exactly where a plausible
history distorts. The #252 pass drafted two entries containing two false
claims: "shipped this way through 843 green tests" (the bug never reached
`main`; adversarial review killed it at 839) and an inventory of where
`tokio::` calls are allowed that `main.rs` and forty `#[tokio::test]` refuted.
Both read as facts and neither was. Before committing anything to `AGENTS.md`,
re-derive every historical claim from `git log -S` and every inventory from a
fresh grep — the file everyone reads first is the worst place to be
approximately right.

**A scripted edit can succeed and still eat the file.** The warning everyone
repeats is the substitution that matches nothing and looks like a success; the
one that cost an amend here was the opposite. Resolving a `.wrap.md` conflict
with a Python slice — `s[:start] + resolved + after` — rebuilt the region
correctly and **truncated everything past it**: one note cut mid-sentence, the
next gone entirely. `markdownlint` reported exactly one problem — MD047, a
missing trailing newline. That is the truncation's *side effect*, not the
truncation: a linter can tell you a file is malformed, never that content is
absent, so the one signal it gave pointed at a one-character fix while two
notes were gone. Read the diff's shape before committing: `git diff --stat`
and a count of removed lines against the number you meant to remove. Six
removed where six were retracted is an answer; forty is a truncation wearing
a nearly clean lint.

**`git cherry-pick --abort` is not an undo for the conflict you were fixing.**
It discards the whole in-progress resolution, including the parts that applied
cleanly and the edits you made by hand. Reached for after a `--continue` that
printed an editor hint instead of committing, it cost the entire merge a second
time. Keep `--abort` for actually abandoning the pick.

For a **single-commit** pick — the case here, and the usual one when rescuing
one orphan commit — `git commit` finishes it and `cherry-pick -n` avoids the
`--continue` step altogether. Neither shortcut generalises: `-n` suppresses the
commit, not the sequencer, so a conflict partway through `cherry-pick -n A B C`
still halts with `.git/sequencer` holding the rest, and only `--continue` walks
it. Know which of the two you are in before reaching for either.

**Squash-merge hides worktree readiness.** `git log main..<branch>` will never
show a merged branch's commits, and `git merge-base --is-ancestor` says NO for
a branch whose content is on `main`. Check `gh pr view <n> --json state`
instead, then remove the worktree and delete the local branch — `git branch -d`
also refuses on the same false premise and needs the PR state, not the graph.
